**风险核心**：今天 WebView 进程内**持有 Agent 长期私钥的完整字节**。WebView 是渲染第三方/半可信内容的地方，任何 XSS 都等价于拿到该身份的完整支配权——不只是"以该身份发消息"，而是"以该身份对任何人、在任何时候、签任意内容"。这是本次审计中唯一必须以 Critical 处理的根因，其余十项要么是它的放大器（SEC-03），要么是"把 WebView 的能力边界继续放大"（SEC-02、SEC-04、SEC-05、SEC-06、SEC-08、SEC-09、SEC-10、SEC-12），要么是"可能造成用户数据不可逆丢失"（SEC-11）。

**本轮的核心判断**：在 §3.4 的整改设计中，P0-2A 的安全收益取决于三件此前被低估的事——

1. **自签名的 `hello` 不是可信身份**（SEC-08）：验签只证明"持有私钥"，不证明"这是用户以为的那个人"；
2. **协议阶段合法 ≠ 业务操作合法**（SEC-09）：`consent_accept` 被允许发出，不代表"用户真的同意了"；
3. **会话同意 ≠ 永久发言授权**（SEC-09）：布尔同意一旦为真，就成了一张无限额发言许可证。

若这三件事不闭环，P0-2A 只是把"WebView 拿着私钥"换成"WebView 拿着一台签名机"。

### 1.4 证据等级口径（与设计文档 §6.3.8 统一）

本报告与设计文档对同一批结论采用**同一套证据等级标注**；**低等级证据不得被表述为高等级结论**：

- **E0 元数据核实** —— 手段：`cargo metadata --locked` / crate 元数据。**能**证明：版本、feature、`rust_version` 等**声明层**事实。**不能**证明：**任何可编译性**、任何运行时行为。
- **E1 依赖树核查** —— 手段：`cargo tree` / `cargo tree -e features`。**能**证明：依赖**构成**（有无 `openssl-sys` / `native-tls` / `system-proxy` / `cmake` 需求）。**不能**证明：**可编译性**、运行时行为。
- **E2 library target 编译级验证** —— 手段：`cargo check --locked --lib`（**仅编译**，**不链接、不运行**）。**能**证明：**特定平台 + 特定工具链 + 特定锁文件状态**下，**库目标**通过编译检查。**不能**证明：完整应用构建、二进制链接、Tauri 应用启动、跨平台构建、运行时安全行为。
- **E3a 全目标编译级验证** —— 手段：`cargo check --locked`（**编译**，**不链接、不产出可运行二进制**；覆盖范围 = **Cargo 默认构建目标范围**，随项目的 Cargo target 配置而定）。**能**证明：**特定平台 + 特定工具链 + 特定锁文件状态 + Cargo 默认构建目标范围**通过编译检查。**不能**证明：最终链接、可运行二进制、Tauri 安装包可用性、跨平台运行时行为。
- **E3b 完整构建级验证** —— 手段：`cargo build --locked`（**编译 + 链接 + 产出构建产物**）。**能**证明：**特定平台 + 特定工具链 + 特定锁文件状态 + 默认构建目标范围**完成**构建与链接并产出构建产物**。**必须保存**：① 命令；② 执行目录；③ Rust 工具链版本；④ 操作系统与架构；⑤ 锁文件状态；⑥ 退出码；⑦ 构建产物位置；⑧ 实际构建目标。**不能**证明：Tauri 安装包打包成功、应用实际启动、运行时权限行为、其它操作系统上的构建、跨平台运行时验收。
- **E4 跨平台 / 运行时验收** —— 手段：**分平台原生**构建 + 打包 + **实际运行**（如 Linux `zenity` 弹窗实弹）。**能**证明：端到端可用性。**必须区分四件不同的事**：① **交叉编译**通过；② **原生平台构建**通过；③ **原生平台打包**通过；④ **原生平台实际运行**通过 —— **交叉编译通过 ≠ 目标操作系统的运行验收通过**。

### SEC-01（Critical）Agent 长期私钥以明文返回 WebView

#### 证据

| 位置 | 事实 |
| --- | --- |
| `apps/desktop/src-tauri/src/lib.rs:183-203` | `invoke_handler` 注册了 `agent_key_get` 等四个 `agent_key_*` command |
| `apps/desktop/src-tauri/src/secrets.rs:250` | `agent_key_get` 直接返回 `entry.get_password()` 的明文 PKCS#8 base64 |
| `apps/desktop/src/lib/tauri-agent-keychain.ts` (`load()`) | 前端通过 `invoke('agent_key_get')` 取回**明文私钥字符串** |
| `apps/desktop/src/lib/agent-service.ts:203,211` | `loadAgent()` 读回私钥并 `return { ...stored, privateKey }` |
| `apps/desktop/src/lib/agent-service.ts:121,144` | `createAgent()` 写入钥匙串后，仍把 `privateKey` 一并返回给调用方 |
| `packages/agent/src/signer.ts:37` | `createEnvelopeSigner` 把该私钥导入 WebCrypto |
| `packages/protocol/src/signature.ts:205-214` | `EnvelopeSigner.sign(input: Uint8Array)` —— **任意字节签名接口** |
| `packages/transport/src/pairing-session.ts:1004-1035` | 出站签名在此处发生，调用方即 WebView |

#### 影响

WebView 内的任意 JS 执行（XSS）可以直接调用 `agent_key_get`，拿到身份私钥的**完整字节**。之后它可以：

1. 在设备离线时签任意内容（无时间戳约束、无会话约束、无类型约束）；
2. 以该身份对**任意第三方**（不只是当前配对的对端）生成合法签名；
3. 把私钥字节外传（`connect-src` 内存在真实的外发通道，见 T4）；
4. 用私钥覆盖掉合法身份，永久劫持该 Agent（`agents_single_local` 唯一索引保证只有一行本地身份）。

关键点：`signature.ts` 里的 `EnvelopeSigner` 是一个**通用字节签名器**，不是"信封签名器"。因此**任何拿到 WebView 内部署的代码**，都不需要经过 `PairingSession` 的状态检查、速率限制、敏感字段防护，就能直接调用 `sign(bytes)` 产出该身份的合法签名。

#### 判定

**Critical**。这不是"私钥存在内存里"的常规问题，而是"长期身份凭据的完全提取"，且提取路径是应用自己提供的。

### SEC-03（Critical）`secret_get` 与 `agent_key_get` 共享同一钥匙串条目

> 本项在上一轮中曾以"SEC-03 High"记录，现为 **Critical**，因为它把 SEC-01 从"一个漏洞"变成"一个漏洞 + 一条绕过 SEC-01 修复的独立路径"。

#### 证据

`keyring` 3.x 的条目由 **(service, username)** 二元组唯一确定。

| 位置 | 事实 |
| --- | --- |
| `apps/desktop/src-tauri/src/secrets.rs:14` | `const SERVICE: &str = "com.kindora.app";` |
| `apps/desktop/src-tauri/src/secrets.rs:23` | `pub const AGENT_KEY_NAME: &str = "agent.identity.p256";` |
| `apps/desktop/src-tauri/src/secrets.rs:88` | `secret_delete` → `Entry::new(SERVICE, &key)` |
| `apps/desktop/src-tauri/src/secrets.rs:250` | `agent_key_get` → `Entry::new(SERVICE, AGENT_KEY_NAME)` |
| `apps/desktop/src-tauri/src/secrets.rs:49-65` | `validate_key` 仅校验"非空 / ≤256 / `[A-Za-z0-9:-_.]`"，**不是命名空间控制** |

因此下面两个命令指向**同一个 OS 钥匙串条目**：

- `secret_get(key = "agent.identity.p256")`
- `agent_key_get()`

而 `"agent.identity.p256"` 恰好满足 `validate_key`（ASCII 字母数字 + `.`），**必然通过校验**。

#### 影响

即使只修复 SEC-01（删除 `agent_key_get`），私钥仍可经 `secret_get` 取回。任何以"删除 `agent_key_get`"为唯一动作的整改方案都是**不完整**的。

同时，`secret_get` 是一个通用的、按调用方提供的 key 读取的命令，且 `secret_list`（`secrets.rs:99`）固定返回空数组——前端只能靠"试 key"来枚举，这本身就是一条可行的探测路径。

#### 判定

**Critical**。它是 SEC-01 的独立绕过路径，且两条路径共用一条修复（服务命名空间隔离 + 白名单化）时必须**同时**完成。

### SEC-02（High）SQL 插件命令权限无 scope，且路径映射可逃逸出应用目录

#### 证据

| 位置 | 事实 |
| --- | --- |
| `apps/desktop/src-tauri/capabilities/default.json` | 权限集含 `core:default`、`store:default`、`sql:default`、`sql:allow-load`、`sql:allow-execute`、`sql:allow-select`、`sql:allow-close` |
| `tauri-plugin-sql 2.5.0` | 四个 command 权限**全部标注 "without any pre-configured scope"**，插件 v2.5.0 **不存在任何 scope 机制** |
| `tauri-plugin-sql 2.5.0` `wrapper.rs::path_mapper` | 实现为 `app_path.push(rest)`：`rest` 为绝对路径时**替换**整个基准路径，为 `../` 时**向上逃逸** |
| `tauri-plugin-sql 2.5.0` `Pool::connect` | 目标文件不存在时**直接创建** |
| `apps/desktop/src/lib/tauri-sql-executor.ts:42,65,77,102` | 前端使用 `sqlite:kindora.db`，并调用 `plugin:sql\|load` / `execute` / `select` |

Tauri v2 的权限集是**并集**语义：`sql:default` 已包含的权限无法通过"移除某个 allow-*"收回。

#### 影响

1. **任意 SQL 执行**：WebView 可执行任意 `SELECT` / `INSERT` / `UPDATE` / `DELETE`，并可执行 DDL（`DROP TABLE`）、`ATTACH`、扩展加载等。
2. **路径逃逸**：带 `sql:allow-load` 时，WebView 可以让插件打开应用目录**之外**的任意 SQLite 文件（甚至创建新文件），远超"读自己的数据库"的授权意图。
3. **数据批量外泄**：结合 T4 的 `connect-src` 白名单中存在的真实外发通道，一次 `SELECT * FROM messages` 即可把完整聊天记录搬走。
4. **`store:default` 是纯粹的额外攻击面**：`packages/` 与 `apps/desktop/src` 中对 `plugin:store` 的调用数为 **0**，该权限当前没有任何合法用途，却额外开放了 14 个 store 操作。

#### 判定

**High**（在 SEC-01 修复后，若 `agent_sign_envelope` 落地而数据库面不收紧，则"能签名的 WebView + 能读全部历史的 WebView"仍是一个完整的数据外泄组合，故本项不因 SEC-01 修复而降级）。

### SEC-04（High）`agent_sign_envelope` 授权模型不完整——XSS 可借助合法签名接口代替用户发消息

> 本项是人工审阅意见要求补充的分析：**"仅验证消息结构和 type 白名单不够，必须分析 XSS 能否利用合法签名接口发送未经用户同意的消息"**。

#### 当前事实（作为整改后的"目标状态"来评估）

`agent_sign_envelope` 是 P0-2A 计划新增的命令。它要替换掉今天"WebView 持有私钥自行签名"的模型。设计上的直接风险是：把"任意字节签名器"换成"信封签名器"，但**只校验信封结构与 type 白名单**——那它仍然是一台**签名机**，只是换了输入格式。

#### XSS 可利用路径（逐步）

| 步 | XSS 动作 | 当前代码中的绕过点 | 结果 |
| --- | --- | --- | --- |
| 1 | `invoke('agent_sign_envelope', {...})` | 若该命令存在，Tauri IPC 对同一窗口内的 JS 全开放 | 直接调用 |
| 2 | 构造 `type = 'consent_accept'` 的信封 | 同意状态机（`packages/matching/src/consent-orchestrator.ts`）**完全在 TS 侧**，Rust 侧不知情 | 绕过"用户已同意"这一前提 |
| 3 | 构造 `type = 'chat_message'` 的信封 | `ChatMessageSource = 'human'`（`packages/matching/src/chat-orchestrator.ts`）**只是 TS 侧的一个字面量**，Rust 侧无从区分"用户输入"与"XSS 构造" | 绕过"人类意图"标记 |
| 4 | 任意指定 `sender` / `recipient` / `timestamp` | Rust 侧当前不解析信封（`apps/desktop/src-tauri/src/lan.rs` 只把消息当不透明字符串写入，见 `write_envelope`） | 可冒用身份、可预签未来时间戳 |
| 5 | 重复签同一个 `messageId` | `ReplayGuard`（`packages/protocol/src/replay-protection.ts`）**只在入站方向生效** | 可批量重放 |
| 6 | 把 API Key 放进 `chat_message` 的 payload | `assertNoSensitiveFields`（`packages/protocol/src/sensitive-field-guard.ts`）在 TS 侧 `PairingSession.send()` 里，绕开 `send()` 即绕开防护 | 凭据可被签给对端 |

#### 关键判断

**"结构合法 + type 在白名单内" 并不等于 "有权签这条消息"。** 一个正确的授权模型至少要回答四个问题，而当前设计一个都没有在 Rust 侧回答：

1. **消息类型授权**：在这种协议阶段下，这种 type 是否允许出站？
2. **会话绑定**：这条消息是否属于当前活跃会话？对端 agent id 是否就是当前绑定的那一位？
3. **用户同意**：这条消息是否代表用户已经做出的决定？
4. **重放防护**：这条 `messageId` 是否已经签过？时间戳是否在窗口内？

#### 判定

**High**。它不是"又多一个漏洞"，而是**决定了 P0-2A 核心机制是否成立**。若授权模型不完整，P0-2A 只是把"WebView 拿着私钥"换成"WebView 拿着一台签名机"，安全收益接近于零。因此本项是 P0-2A 的**阻断性验收项**，不是可选项。

> 🆕 **v3 扩写**：本轮审阅进一步指出，即使上述四问全部回答"是"，**第五问仍未被回答**——"用户同意"是一个**布尔量**，"这条消息是否**现在**还代表用户当前的意图"。该缺口已单列为 **SEC-09**，因为它的修复方式（消息级授权）与 SEC-04 的修复方式（闸门矩阵）不同。

### SEC-05（High）`db_exec` 缺少逐操作的数据可见性边界

> 本项对应人工审阅意见：**"Rust 侧不能仅仅固定 SQL，还必须明确每种操作可以读取和返回哪些数据，防止 XSS 通过合法数据库操作批量读取用户敏感信息"**。

#### 当前事实

`packages/storage/src/sqlite-database.ts` 用**固定 SQL 文本**实现 `KindoraDatabase`（`packages/storage/src/database.ts:128-198`）的 20 个操作，SQL 由 TS 侧拼装后经 `plugin:sql|execute` / `plugin:sql|select` 执行。也就是说：**SQL 语句本身在 WebView 进程里**。

若只做"把 SQL 文本挪到 Rust 侧固定"，而不定义"每个操作能返回哪些列、多少行、多快一次"，WebView 依然可以：

- 用 `listMessages(sessionId)` 一次性拉走**全部会话**的完整聊天记录（`messages.text` 存明文正文）；
- 用 `listSessions()` 拿到全部会话与对端身份；
- 用 `listBlockedAgents()` 拿到黑名单；
- 用 `getSetting(key)` 读取任意 `settings` 表键（当前表是通用的 `key/value`，不是固定表）。

#### 需要明确的四类边界

| 边界 | 含义 |
| --- | --- |
| **列投影** | 每个操作只返回其用途所需的列，不返回整行（例如 `agents` 表的 `private_key_storage_json` 永不出 Rust） |
| **行数上限** | 读操作有硬性 `LIMIT` 与游标分页，单次调用不可能返回无界结果集 |
| **速率上限** | 按操作 / 按会话限速，使"批量外泄"在时间维度上不可行（对抗 T4 的外发通道） |
| **审计** | 每次操作在 Rust 侧留痕（操作名、参数摘要、返回行数），不记录 payload 正文 |

#### 判定

**High**。数据库里装的是用户最敏感的数据（完整私聊正文）。把 SQL 固定下来是**必要但不充分**的；没有上述四类边界，"合法 DB 操作"仍然是一条高效的数据外泄管道。

> 🆕 **v3 扩写**：本轮审阅进一步指出，上述四类边界**全部是"数据维度"的**（哪些列、多少行、多快一次）。它们**不回答"这一行属于谁"**。该缺口已单列为 **SEC-10**。

### SEC-06（Medium）Secret key 校验是字符集校验而非命名空间白名单

> 本项对应人工审阅意见：**"明确 Secret 白名单对大小写、编码变体、未知 provider 和非法 key 的拒绝策略，并保证 set/get/delete 使用一致规则"**。

#### 当前事实

`secrets.rs:49-65` 的 `validate_key` 只检查三件事：非空、长度 ≤ 256、字符集属于 `[A-Za-z0-9:-_.]`。**任何**满足这三点的 key 都能读写。因此下列 key 当前**全部合法**：

| Key | 当前行为 | 问题 |
| --- | --- | --- |
| `llm:openai-compatible:api-key` | 合法 | 这是真正合法的 key |
| `llm:anthropic:api-key` | 合法 | 合法 |
| `llm:ollama:api-key` | 合法 | `providerRequiresApiKey` 对 ollama 为 false，本不该有 key（**Q4 已决定保留**该 key，见下） |
| `llm:minimax:api-key` | 合法 | 合法 |
| `agent.identity.p256` | **合法** | ← SEC-03 的绕过路径 |
| `LLM:OpenAI:api-key` | **合法** | 大小写变体 = 另一个钥匙串条目 → 别名分裂 |
| `llm%3Aopenai%3Aapi-key` | **合法** | 百分号被拒，但 `llm:openai%3Aapi-key` 之类混合形式仍可作别名 |
| `llm:evil-provider:api-key` | **合法** | 未知 provider 仍可写入一条无人消费的数据 |
| `../../etc/passwd` | **合法**（`.` 与 `/`… 注意 `/` 不在字符集内） | 实际被字符集拦下，但这是"运气"而非"设计" |

> **Q4 决定**：`llm:ollama:api-key` **保留在白名单内**（尽管 ollama 实际不需要 key），以便兼容既有配置。设计上须保证"保留但不被消费"不产生歧义（见设计文档 §4.2.3）。

#### 判定

**Medium**。单独看是纵深防御缺失，但它是 SEC-03 得以成立的技术前提，且修复成本极低。

### SEC-07（Medium）密钥迁移顺序与回滚策略存在可导致私钥丢失 / 重新暴露的设计缺陷

> 本项对应人工审阅意见的两条要求：**"删除任何通过 feature flag 重新启用 `agent_key_get` 或旧 JavaScript 私钥签名路径的回滚方案"** 与 **"钥匙串迁移必须遵循先写新条目、读回校验、确认成功后才删除旧条目"**。

#### 当前事实

`apps/desktop/src/lib/agent-keychain-migration.ts` 已经示范了正确的**库内**顺序（写 → 读回比对 → 改写记录 → 读回确认，失败时把旧记录写回）。这是好的。但本轮 P0-2A 的整改是**跨命名空间**的迁移（`("com.kindora.app", "agent.identity.p256")` → 新的服务名），需要一条**新的**迁移序列，其顺序约束比库内迁移更强：

1. 迁移必须在**两个命名空间同时可用**的窗口内完成（否则任一时刻只有一份私钥）；
2. 旧条目的删除必须**严格晚于**新条目的写入与校验；
3. 任何一步失败都**不得**导致"唯一私钥副本丢失"；
4. **不得**存在任何运行时开关可以重新启用 `agent_key_get` 或旧 JS 签名路径。

第 4 条尤其关键：如果回滚方案是"加个 feature flag 恢复旧路径"，那么整改就只是**推迟**了漏洞，而不是消除它——攻击者只需要等待或诱导用户启用该 flag。正确做法是让回滚的粒度等于**发布版本**，并且保证旧版本在新版本失败时仍然可用。

> 🆕 **v3 确认（Q1）**：本轮审阅**确认接受**"删除旧条目"与"写入新条目"分离（M1/M2）的方案，要求：① **保留回滚窗口**；② **迁移失败时旧条目保持一字不变**。这两条已固化为设计文档 §4.5.3 的不变量 I1–I7 与 §4.5.5 的故障注入测试。

#### 判定

**Medium**（本身不是可被直接利用的漏洞，但它是**整改方案本身的正确性前提**；若设计错误，整改会产生比现状更差的结果——私钥永久丢失）。

### 🆕 SEC-08（High）配对身份绑定只单向生效且完全位于 WebView 内

> 对应人工审阅意见：**"必须区分首次 `hello` 的自签名验证与身份可信验证，并明确配对身份绑定规则"**。

#### 概念区分（本项的立论基础）

| 概念 | 定义 | 由什么得到 | **不能**推出 |
| --- | --- | --- | --- |
| **密钥持有证明（PoK）** | "持有该私钥的一方签了这条 `hello`" | 对入站 `hello` 的**签名验签通过** | ❌ **不能推出**"该公钥属于用户所认定的那个对端" |
| **身份归属证明（PoA）** | "该公钥属于用户所认定的那个对端" | **带外（out-of-band）人工核对指纹** | — |

**自签名的 `hello` 不能直接视为可信身份**——它只满足 PoK。

#### 当前事实（逐条核实）

| # | 事实 | 证据 |
| --- | --- | --- |
| G1 | 带外指纹检查**只存在于 WebView**（TS），XSS 可完全绕过 | `packages/transport/src/pairing-session.ts:955-962`（`expectedPeerFingerprint` → `derivePairingFingerprint` → `fingerprintsMatch` → `failSecurity('peer-fingerprint-mismatch')`） |
| G2 | 期望指纹**只在 join（加入）侧**设置；**host（主机）侧从不设置** | `apps/desktop/src/lib/connect-service.ts:256`、`apps/desktop/src/lib/lan-connect-service.ts:620` 有 `expectedPeerFingerprint`；`connect-service.ts:174` 的 host 路径**没有** |
| G3 | **Rust 侧零指纹逻辑** | `grep -rn "fingerprint" apps/desktop/src-tauri/src/` → 无命中 |
| G4 | UI **只展示主机侧的配对码**，加入方**不展示**自己的指纹 | `apps/desktop/src/views/ConnectView.tsx:475` `data-testid="host-pairing-code"`；无 joiner 指纹展示元素 |
| G5 | 指纹派生算法已在 TS 实现且语义明确 | `packages/transport/src/pairing-fingerprint.ts`：`CrockfordBase32(SHA-256(utf8(agentId) ‖ SPKI_DER))[0..6]`，字母表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`；`fingerprintsMatch` 忽略大小写与短横线 |

#### 影响

1. **主机侧对加入方没有任何身份绑定**（G2）。在 LAN 上，一个抢在合法用户之前应答设备发现广播的敌对设备可以完成配对，而**主机侧不会发现**（T6）。
2. **即使在 join 侧，带外检查也可被 XSS 绕过**（G1 + G3）：整个配对安全性质建立在 WebView 内的一段 TypeScript 上，而 WebView 正是威胁模型 T1 中"不可信"的那一层。Rust 侧没有任何可作为权威判定的实现。
3. **协议层已经具备做双向绑定的全部信息**：`hello` 已携带 `sender` 与 `publicKey`，双方都能派生指纹（G5）——**不需要任何协议格式变更**。

#### 判定

**High**。这不是"功能缺失"，而是**安全边界建立在错误的一层**。它使"配对码机制"在生产形态（Tauri）下**只提供了一半的保护**，而用户会以为它是完整的。

### 🆕 SEC-09（High）协议阶段合法被当作业务操作合法；会话同意等价于永久发言授权

> 对应人工审阅意见：**"必须增加 payload 业务语义校验与消息级授权；协议阶段合法不等于业务操作合法"** 与 **"会话同意不得等于永久发送授权"**。

#### 两个缺口

**缺口 A —— 只有"阶段 × 类型"矩阵，没有业务语义校验。**

授权矩阵回答的是"这种 type 在这种协议阶段能不能发"。它**不**回答：

| 问题 | 例 |
| --- | --- |
| 这条消息在**当前会话状态**下说得通吗？ | 会话里连 `hello` 都没收到，就来一条 `profile_exchange`？ |
| 这个业务对象是否**已存在**？ | 没有发出过 `match_request`，对方回一个 `match_response`？ |
| 卡片内容是否符合当前阶段的**可见性**要求？ | 尚未同意，就发完整个人资料（`filterProfileForOutbound` 的完整卡）？ |
| 文本是否**非空、是否与上一条重复**？ | `chat_message.text = "   "` 或连发两条一模一样的文本？ |
| 是否存在**未决**的同类请求？ | 同时挂 3 个 `permission_request`？ |

由于 TS 侧的校验器（`packages/protocol/src/validation.ts`）**完全在 WebView 内**，XSS 可绕过；Rust 侧若只实现形状校验，同样留下缺口。

**缺口 B —— `consent` 是一个布尔量，等价于一张无限额发言许可证。**

v2 设计的授权模型中，`consent_local && consent_peer` 一旦为真，`chat_message` 就被**永久允许**：没有条数上限、没有时限、不可撤销、消耗无痕迹。**这实质上是把"用户曾经同意过一次"翻译成"WebView 从此可以无限期地以用户身份发言"**。

#### 现状是否更糟？

现状（WebView 持有私钥）当然**更糟**：XSS 不需要同意，直接签即可。但这正是问题所在——如果 P0-2A 只把"无限"换成"需要一次布尔同意"，那么整改后 XSS 仍然可以在**用户点过一次"同意聊天"之后**无限期代用户发言，且用户没有任何可见信号。**这不满足审阅意见。**

#### 影响

1. 用户的一次点击，被解释为一份**无限期的、无感知消耗的**代理发言权；
2. 用户界面**无法显示**还有多少"额度"，因此异常消耗不可察觉（不可审计、不可察觉 = 不可抑制）；
3. 与之叠加的是 SEC-08：既然对端身份可能根本没被核对过，那么"在一个身份未确认的会话里无限发言"的后果更严重。

#### 判定

**High**。这是 P0-2A 的**第二个阻断性验收项**：与 SEC-04 同级。若不修复，P0-2A 的安全收益在"用户点过一次同意"这个最常见场景下接近于零。

### 🆕 SEC-10（High）数据库授权只有列投影，缺逐对象 / 逐会话的归属检查

> 对应人工审阅意见：**"必须增加逐操作、逐对象、逐会话的数据库数据访问授权，仅靠列投影是不够的"**。

#### 当前事实与设计缺口

现有 `KindoraDatabase`（`packages/storage/src/database.ts:128-198`）的 20 个操作**全部以 `sessionId` / `agentId` / `key` 作为自由参数**。前端的 `tauri-sql-executor.ts` 把这些参数原样拼进 SQL。

SEC-05 的四类边界都是**数据维度**的：哪些列、多少行、多快一次、是否留痕。它们**不回答"这一行属于谁"**：

| 缺口 | 具体表现 |
| --- | --- |
| **逐对象缺失** | `db_get_agent(agentId)` 若只做列投影（不返回 `private_key_storage_json`），则传**任意** agentId 都会返回**别人的**公开资料行；`db_update_message_status(messageId, status)` 若只做列投影，则可改**任意会话**的消息状态 |
| **逐会话缺失** | `db_list_messages(sessionId)` 只要 sessionId 格式正确就能读**任意历史会话**的完整正文；WebView 无需真正参与过该会话 |
| **归属自洽缺失** | `db_append_message(sessionId, direction, ...)` 的 `sender_agent_id` 与 `direction` 之间**没有一致性约束**，可写入方向与发送者互相矛盾的记录 |

#### 影响

在"列投影 + LIMIT + 速率 + 审计"之上仍留有**越权读取/篡改**的通道：

- WebView 可**遍历**历史会话（枚举 sessionId 即可），把速率限制降级为"慢速全量外泄"；
- WebView 可**篡改**其他会话的消息状态（伪造"已读""失败"）；
- 速率限制是**全局**的 ⇒ 一个会话就能吃光全局预算，其他会话的正常读取被饿死（可用性 + 掩盖）。

#### 判定

**High**。列投影是**必要但不充分**的；授权必须落到**操作 / 对象 / 会话**三个粒度上。

| **Linux** | `~/.config` | `~/.local/share` | **不同** ⚠️ |

⇒ **旧库真实路径**：macOS `~/Library/Application Support/com.kindora.app/kindora.db`；Windows `%APPDATA%\com.kindora.app\kindora.db`；Linux `~/.config/com.kindora.app/kindora.db`。

#### 影响

1. **静默创建空库**：旧插件在目标文件缺失时**直接创建一个空库**并继续运行（`wrapper.rs:96-98`）。用户看到的是"聊天记录全没了"，而**没有任何错误提示**。当 P0-2B 把数据库访问权从插件移交到新的 Rust 层时，如果新层沿用了同样的"不存在就建"的逻辑，就会把旧插件的这个缺陷**继承**下来。
2. **平台差异陷阱**：`app_config_dir()` 与 `app_data_dir()` 在 **Linux 上不同**（`~/.config` vs `~/.local/share`），在 macOS / Windows 上相同。这意味着**在 macOS 上测不出来的路径错误，在 Linux 上就是"用户数据全部消失"**——而 Kindora 桌面端恰好有 Linux 构建目标（P0-1 刚为 Linux CI 装好 Tauri 依赖）。
3. **不存在"路径一致"的证明**：只要新层是**自己拼路径**（而不是调用同一个 `app.path().app_config_dir()`），就没有任何机制保证两条路径永远一致。

#### 判定

**High**。这不是可被利用的"信息泄露"，但是**用户数据不可逆丢失**的风险；在 Linux 上由"配置差异"直接触发，且失败模式是**静默**的。

## 3. 跨发现关联分析

单看每一项，修复难度不同；放在一起看，它们构成一条**必须一次性切断的链**：

```
  XSS in WebView
      │
      ├─► (SEC-01) agent_key_get ──────────► 私钥完整字节
      │        └─► (SEC-03) secret_get("agent.identity.p256") ──► 同一条目，同一结果
      │
      ├─► (SEC-04) agent_sign_envelope ────► 代替用户发消息（同意/聊天）
      │        └─► (SEC-09) 同意 == 永久发言授权（无额度/无时限/不可撤销）
      │        └─► (SEC-09) 只查阶段×类型，不查业务语义
      │
      ├─► (SEC-08) 配对身份绑定（单向 + 仅 WebView）──► 对端可能根本不是用户以为的那个人
      │        └─ 与 SEC-04 叠加：在"身份未确认"的会话里发言，后果更重
      │
      ├─► (SEC-12) secret_get ─────────────► LLM API Key 明文
      │        └─► connect-src 内的 LLM 端点 ──► 真实外泄通道（既是出口，也是"以受害者账户消费"）
      │
      └─► (SEC-02) plugin:sql|execute ─────► 任意 SQL
               └─► (SEC-05) 合法 DB 操作 ────► 批量读取私聊正文
                        └─► (SEC-10) 无逐对象/逐会话归属检查 ──► 越权遍历历史会话
                        └─► (SEC-11) 路径/静默建空库 ──► 用户数据不可逆丢失
```

### 3.1 依赖关系（决定了实施顺序）

| 依赖 | 内容 |
| --- | --- |
| SEC-01 + SEC-03 + SEC-04 | 必须在**同一个 PR（P0-2A）**中一起完成，否则 SEC-04 会把 SEC-01 的修复抵消掉 |
| SEC-08 → SEC-04 | 身份绑定**必须先于**或**同时**于**发言授权落地；否则"对谁都敢说话" |
| SEC-09 → SEC-04 | 消息级授权是 SEC-04 的**必要补充**，不是可选加固 |
| SEC-05 + SEC-10 | 必须在**同一个 PR（P0-2B）**中一起完成；列投影单独上线不构成授权 |
| SEC-11 | 是 P0-2B 的**前置**：数据库层接管前必须先把路径与"禁止静默建空库"钉死 |
| SEC-12 | 依赖 **A-LLM**（TLS 依赖论证）。**v4：可独立推迟的选项已废止** —— A-LLM 是 **P0-2A 的合并阻断条件**（设计文档 §8.1.1 MB-1…MB-5） |

### 3.2 分成两条独立任务线的原因

SEC-01/03/04/08/09/12 属于**身份与授权面**（P0-2A）；SEC-02/05/10/11 属于**数据面**（P0-2B）。两者**不能**只做一半——这正是把 P0-2 拆成 P0-2A / P0-2B 两条独立任务线的原因：它们各自内部必须自洽，各自独立验收。
